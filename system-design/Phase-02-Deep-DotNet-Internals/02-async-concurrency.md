# Async & Concurrency

> **Phase:** 2 — Deep .NET Internals  
> **Status:** Not Started

## Overview

Async and concurrency are at the heart of building scalable .NET services. This section goes beyond knowing how to use `async/await` to understanding what the compiler generates, how the thread pool schedules work, and how to design concurrent systems that are correct, efficient, and debuggable under load.

## Topics

### async/await Internals

**What it is:** A compiler transformation that converts `async` methods into state machines — objects that capture local variables and execution position, resuming on each `await` completion.

**Why it matters:** Understanding the state machine reveals why `async` has overhead, what causes allocations, and why certain patterns (like awaiting in loops) can cause issues.

**Key concepts to understand:**
- The state machine struct/class generated by the compiler: `IAsyncStateMachine`
- `MoveNext()` as the entry point: each await point is a switch case
- How local variables are hoisted to state machine fields (heap allocation implication)
- The `AsyncTaskMethodBuilder<T>` and when it avoids heap allocation
- Exception capture in async methods: exceptions are stored in the Task, not thrown immediately
- `AsyncMethodBuilderAttribute`: custom builders for pooling state machine allocations

### SynchronizationContext

**What it is:** An abstraction that controls where continuation code (code after `await`) resumes — in ASP.NET Core there is no SynchronizationContext, but in UI frameworks it ensures UI thread affinity.

**Why it matters:** `SynchronizationContext` captures in library code can cause deadlocks in legacy ASP.NET (classic) or cause unnecessary thread switches — understanding it explains `ConfigureAwait(false)`.

**Key concepts to understand:**
- `SynchronizationContext.Current` and how it's captured at each `await`
- `WindowsFormsSynchronizationContext` / `DispatcherSynchronizationContext`: marshal to UI thread
- `AspNetSynchronizationContext` (classic ASP.NET): one request at a time — deadlock source
- ASP.NET Core: no synchronization context by default — continuations run on thread pool
- `SynchronizationContext.SetSynchronizationContext` and testing implications
- `ExecutionContext` vs `SynchronizationContext`: logical call context propagation vs scheduling

### ConfigureAwait

**What it is:** `ConfigureAwait(false)` instructs the awaiter not to capture the current `SynchronizationContext`, allowing the continuation to run on any thread pool thread.

**Why it matters:** Library code should always use `ConfigureAwait(false)` to avoid deadlocks in consumers that use synchronization contexts, and to avoid unnecessary context switches.

**Key concepts to understand:**
- `ConfigureAwait(false)` prevents context capture: continuation runs on completing thread
- Why `ConfigureAwait(false)` doesn't matter in ASP.NET Core (no sync context)
- The deadlock pattern: sync-over-async with `Task.Result` + sync context that queues work
- `ConfigureAwait(continueOnCapturedContext: true)` for UI code needing thread affinity
- Analyzers: `ConfigureAwaitChecker.Analyzer` or Roslyn analyzers to enforce `ConfigureAwait(false)` in library code
- .NET 6+ `ConfigureAwaitOptions.SuppressThrowing` for task composition scenarios

### ThreadPool Internals

**What it is:** The .NET runtime's managed pool of worker threads that executes `Task`-based work items, I/O completion callbacks, and timer callbacks without creating a new thread per task.

**Why it matters:** Thread pool starvation (all threads blocked on sync I/O) is a common cause of cascading failures in microservices — understanding the pool prevents and diagnoses this.

**Key concepts to understand:**
- Work stealing: each thread has a local deque; idle threads steal from others
- Hill-climbing algorithm: the pool dynamically adjusts thread count based on throughput
- Thread injection: slow (seconds) by design — avoid long-running sync work items
- `ThreadPool.SetMinThreads`: pre-warming the pool for services with bursty load
- `ThreadPool.QueueUserWorkItem` vs `Task.Run`: same underlying mechanism, `Task.Run` adds Task wrapper
- Diagnosing starvation: `ThreadPool.GetAvailableThreads`, ETW events, `dotnet-counters`

### TaskScheduler

**What it is:** An abstraction that controls how `Task` objects are queued and executed — the default scheduler uses the thread pool, but custom schedulers can target specific threads or execution environments.

**Why it matters:** Understanding `TaskScheduler` enables building specialized execution contexts: UI-thread schedulers, test schedulers, priority schedulers, and throughput-limited schedulers.

**Key concepts to understand:**
- `TaskScheduler.Default`: thread pool scheduler
- `TaskScheduler.Current` vs `TaskScheduler.Default`: inside a scheduled task vs global default
- `ConcurrentExclusiveSchedulerPair`: reader-writer scheduling for tasks
- `SynchronizationContextTaskScheduler`: wraps a SynchronizationContext as a scheduler
- Custom scheduler implementation: override `QueueTask`, `TryExecuteTaskInline`, `GetScheduledTasks`
- `TaskFactory` with custom scheduler for `Task.Factory.StartNew` with explicit scheduler

### CancellationToken Patterns

**What it is:** A struct-based cooperative cancellation mechanism where operations check a `CancellationToken` and throw `OperationCanceledException` when cancellation is requested.

**Why it matters:** Proper cancellation propagation prevents resource waste and enables graceful shutdown — incorrect usage leads to operations running long after the client has disconnected.

**Key concepts to understand:**
- `CancellationTokenSource`, `CancellationToken`, and `CancellationTokenRegistration`
- Linked token sources: `CancellationTokenSource.CreateLinkedTokenSource` for combining timeouts with request cancellation
- `token.Register(callback)`: run synchronous cleanup on cancellation
- `OperationCanceledException` vs `TaskCanceledException`: the latter inherits from the former
- Cancellation in ASP.NET Core: `HttpContext.RequestAborted` token
- Avoiding cancellation token proliferation: pass through layers, don't create new tokens at each layer
- Timeout pattern: `CancellationTokenSource` with `CancelAfter` for operation timeouts

### Channels

**What it is:** `System.Threading.Channels` provides high-performance, thread-safe producer-consumer queues with backpressure support and async read/write operations.

**Why it matters:** Channels replace `ConcurrentQueue<T>` + polling with a clean async API — they're the right primitive for in-process producer-consumer pipelines with flow control.

**Key concepts to understand:**
- `Channel.CreateUnbounded<T>()` vs `Channel.CreateBounded<T>(capacity)`: unbounded has no backpressure
- `BoundedChannelFullMode`: Wait, DropWrite, DropRead, DropNewest, DropOldest
- `ChannelWriter<T>.TryWrite` vs `WriteAsync`: synchronous fast path vs async slow path
- `ChannelReader<T>.ReadAllAsync()`: async enumerable over all items until channel is completed
- Single-producer single-consumer vs multi-producer multi-consumer performance characteristics
- Composing channels into pipelines: connect ChannelReader to ChannelWriter between stages

### Pipelines

**What it is:** `System.IO.Pipelines` provides a high-performance, memory-efficient async I/O API designed for network protocols, replacing stream-based I/O with a pipe of owned memory segments.

**Why it matters:** Pipelines eliminate the double-buffering and copying inherent in stream-based reading — they're used in Kestrel, SignalR, and any code parsing network protocols at high throughput.

**Key concepts to understand:**
- `PipeWriter` / `PipeReader`: producer and consumer ends of a Pipe
- `GetMemory(sizeHint)` + `Advance(bytesWritten)`: zero-copy write pattern
- `ReadAsync()` returns `ReadResult` with a `ReadOnlySequence<byte>` (potentially non-contiguous)
- Backpressure: `PauseWriterThreshold` and `ResumeWriterThreshold` on `PipeOptions`
- Parsing patterns: examining sequence, marking consumed vs examined positions
- Integration: `SocketPipeTransport` in Kestrel as a real-world example

### ValueTask

**What it is:** A value-type alternative to `Task<T>` that avoids heap allocation when an async operation completes synchronously — useful for hot paths where most calls don't actually need to wait.

**Why it matters:** In high-throughput code (e.g., reading from a socket that usually has data), `ValueTask<T>` can eliminate millions of allocations per second compared to `Task<T>`.

**Key concepts to understand:**
- `ValueTask<T>` is a struct wrapping either a `T` (synchronous result) or a `Task<T>`/`IValueTaskSource<T>` (async result)
- Rules for correct use: only await once, don't cache, don't call `GetAwaiter().GetResult()` on an incomplete `ValueTask`
- `IValueTaskSource<T>`: the low-level interface for poolable async state machines
- `ManualResetValueTaskSourceCore<T>`: reusable source for avoiding allocations in tight loops
- When NOT to use `ValueTask`: when results are rarely synchronous (allocates `Task` anyway), when awaited multiple times
- `ValueTask` in `System.IO.Stream` async methods: the pattern in the BCL

### IAsyncEnumerable

**What it is:** An interface (`IAsyncEnumerable<T>`) that enables async iteration — producing items one at a time asynchronously, consumed with `await foreach`.

**Why it matters:** `IAsyncEnumerable<T>` models streaming results from databases, queues, and APIs without buffering all results in memory — essential for efficient large data set processing.

**Key concepts to understand:**
- `await foreach` syntax and the `GetAsyncEnumerator(CancellationToken)` contract
- `yield return` in `async` methods: the compiler generates an async state machine iterator
- `WithCancellation(token)` on `IAsyncEnumerable<T>` to pass cancellation
- `ConfigureAwait(false)` on `IAsyncEnumerable<T>`: use `ConfigureAwait` on the `await foreach`
- EF Core `AsAsyncEnumerable()`: streaming database results without loading into a list
- Channel as an async enumerable source: `reader.ReadAllAsync()`

### Producer-Consumer Patterns

**What it is:** A concurrency design pattern where producer threads generate work items and consumer threads process them, decoupled through a shared queue or channel.

**Why it matters:** Producer-consumer is the backbone of pipeline architectures, background processing systems, and message-driven designs — getting it right (backpressure, ordering, error handling) is non-trivial.

**Key concepts to understand:**
- Bounded queue as a backpressure mechanism: slow consumers automatically slow producers
- Work stealing for load balancing across multiple consumers
- Ordering guarantees: FIFO channels vs priority queues vs unordered parallel processing
- Error handling: dead-letter queue vs retry queue vs fail-fast propagation
- Fan-out: one producer, multiple consumers — each gets all messages vs work distribution
- `Dataflow` (TPL Dataflow): `ActionBlock`, `TransformBlock`, `BufferBlock` for pipeline composition

### Lock Contention

**What it is:** The performance penalty that occurs when multiple threads compete for the same lock, causing some threads to spin or block while waiting.

**Why it matters:** Lock contention is a primary cause of poor scalability in concurrent systems — identifying and reducing hot locks is a key performance engineering skill.

**Key concepts to understand:**
- Thin lock, fat lock, and spin lock progression in CLR's Monitor implementation
- Lock convoy: a high-contention lock where threads build up behind a slow holder
- False sharing: separate objects on the same cache line causing unnecessary cross-core traffic
- Lock granularity: coarse vs fine-grained locking tradeoffs
- Striped locking: dividing a shared resource into independent segments each with its own lock
- `Interlocked` operations for atomic counter updates without lock overhead

### SemaphoreSlim

**What it is:** A lightweight semaphore that limits concurrent access to a resource, supporting both synchronous waiting and async waiting (`WaitAsync()`).

**Why it matters:** `SemaphoreSlim` is the go-to primitive for limiting concurrency (e.g., max 10 concurrent database connections, throttling outbound API calls) in async code.

**Key concepts to understand:**
- `SemaphoreSlim(initialCount, maxCount)`: initialCount = current permits, maxCount = maximum
- `WaitAsync()` for async waiting vs `Wait()` for sync waiting (avoid sync wait in async code)
- `Release(releaseCount)` to return permits
- Using as a throttle: wrap operations in `WaitAsync` / `Release` pairs in try-finally
- Fairness: `SemaphoreSlim` is generally FIFO for waiting tasks
- `SemaphoreSlim` as a binary semaphore (mutex alternative) for async exclusion

### ReaderWriterLockSlim

**What it is:** A lock that allows multiple concurrent readers OR a single exclusive writer, providing higher throughput than a mutex for read-heavy workloads.

**Why it matters:** In-memory caches, configuration providers, and other read-heavy shared state benefit significantly from `ReaderWriterLockSlim` vs a simple `lock`.

**Key concepts to understand:**
- Three modes: read lock, upgradeable read lock, write lock
- Read locks: concurrent, non-exclusive; write lock: exclusive, blocks all readers and writers
- Upgradeable read lock: allows atomically upgrading to write lock without releasing and re-acquiring
- Lock recursion policy: `LockRecursionPolicy.NoRecursion` (default, prevents reentrancy) vs `SupportsRecursion`
- Starvation risk: continuous reader load can starve writers
- `ReaderWriterLockSlim` vs `Interlocked` immutable swap: for many scenarios, replacing the reference is simpler and faster

### Lock-Free Programming Basics

**What it is:** Concurrent programming techniques using atomic operations (compare-and-swap, fetch-and-add) instead of locks to coordinate access to shared data without blocking.

**Why it matters:** Lock-free structures eliminate contention overhead and prevent thread blocking — they underpin high-throughput components like the thread pool, channels, and memory allocators.

**Key concepts to understand:**
- Compare-and-swap (CAS): atomically check and update a value — the foundation of most lock-free algorithms
- `Interlocked.CompareExchange`: CAS in .NET
- ABA problem: a value changes from A to B and back to A — CAS succeeds incorrectly; solutions include version counters
- Memory ordering: `Volatile.Read/Write`, `Thread.MemoryBarrier` for visibility guarantees
- Lock-free stack (Treiber stack): push/pop via CAS on head pointer
- Progress guarantees: lock-free (some thread always makes progress) vs wait-free (every thread always makes progress)
